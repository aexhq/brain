# ADR-033: Distinguish resident Tools from explicitly placed extensions

- Decision date: 2026-09-05
- Status: Accepted
- Compiled: 2026-09-05

Amended by: [ADR-041: Run every Tool in an Environment that implements one protocol, including Brain's own](2026-09-05-10-one-execution-model.md), which replaces the two Tool forms with one: every Tool is placed in an Environment, and the application host is the host env.

Supersedes: [ADR-016: Terminate application Tool channels in Brain](2026-09-01-01-client-channels.md); [ADR-028: Expose independently created and shared Environment resources](2026-09-04-06-shared-environments.md).

## Context

The same abstraction had to support code already running in an application and packaged code executed elsewhere. Treating both as callback Environments added synthetic resources; automatic language/runtime selection hid authority and lifecycle decisions.

## Decision

A resident Tool uses its application’s run function and needs no synthetic Environment. The SDK registers a resident host, receives commands over a bounded SSE stream, and posts results and emitted Events over HTTP. A placed Tool or Agentloop is configured with exactly one explicit `{ env, ...options }` binding at session creation. Native implementations are admitted Components; other descriptors are opaque to their selected driver.

## Alternatives considered

A separate app callback service, implicit placement, runtime inference, package installation, and automatic fallback all add policy beyond the chosen MVP. Generic Environment declarations remain open-ended, but the current server runs Agentloops only through brainWasm; arbitrary remote Agentloops are not a shipped claim.

## Consequences

An Environment declaration belongs to one session, and reusing an SDK object creates a new logical declaration for another session. Remove the standalone shared-Environment API until its semantics can be supported. Code and capabilities are prepared before readiness; physical resource allocation may be lazy. Driver route names and their credentials are deployment grants: a session cannot choose an arbitrary destination for a server-held credential. Losing a resident host makes an in-flight outcome unknown; Brain does not replay it. Application-resident code retains its application’s ambient authority.
