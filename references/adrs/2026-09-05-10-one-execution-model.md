# ADR-041: Run every Tool in an Environment that implements one protocol, including Brain's own

- Decision date: 2026-09-05
- Status: Proposed
- Compiled: 2026-09-05

Extends: [ADR-022: Let Environments execute implementations using their own platform APIs](2026-09-02-05-resources.md), whose create-time check of Tool needs against declared resources this record removes; [ADR-033: Distinguish resident Tools from explicitly placed extensions](2026-09-05-02-placement.md); [ADR-040: Identify records by session and sequence, and everything inside a session by name](2026-09-05-09-session-names.md).

## Context

Brain describes two ways a Tool can run: placed in an Environment that Brain reaches over HTTP, or inside the application that created the session, reached over a connection the application holds open. The distinction leaks into every layer. A Tool carries a `hosting` flag, a `host_id` beside an optional `environment_id`, and six cross-field validation rules that say which of those may be present together. The dispatcher branches on the flag. The host registration table is an Environment lifecycle in disguise: it tracks the sessions each registered host serves, adds one at create, and removes it at end. Where an HTTP Environment lives is decided by a routes file the server operator writes, so an Environment extension cannot let the application configure its own address.

The built-in Wasm Environment is a third path. Its driver name is matched as a string in seven places: the route name is reserved, its declared resources are derived from its configuration by Brain instead of answered by it, the dispatcher has a dedicated configuration lookup, the registry fakes its setup and attach receipts and refuses to route an invoke through the ordinary path, only it may run an Agentloop, only Component implementations are accepted in it, and the dispatcher has a native branch to the worker. The Agentloop turn bypasses the Environment layer entirely. The SDK names the Environment after its runtime, `brainWasm`, and stores the driver name inside the configuration object the driver receives, so the server has to read it back out of the driver's own options.

Brain also stands between a Tool and its Environment in ways neither asked for. An Environment declaration holds plaintext binding values that ride on the attach request and are redacted from the journal. A Tool lists binding names that Brain validates for shape and forwards, but never checks against the Environment; the docs describe a check that the driver may or may not perform. A Tool lists resource names it needs, an Environment answers setup and attach with the resources it declares, and Brain compares the two at create, owning a resource-name grammar and a declaration format for the purpose. An Environment therefore has to declare everything it could offer before it knows which Tools will run in it. Setup and attach are two operations because ADR-028 shared one Environment across sessions; since ADR-033 they always happen together, once, at create.

## Decision

1. A Tool runs in an Environment. There is one execution model, not two. Every Tool names exactly one Environment of its session. `hosting` and the Tool-level `host_id` are removed, and with them the validation rules that policed their combinations.
2. An Environment is anything that implements the Environment protocol. Where it runs is the Environment's concern, and how Brain reaches it is the only thing Brain reads about it. An Environment extension defines its own options and lets the application configure each instance, for example `awsMicroVm({ url, region, token })`; Brain reads the `url` and an optional credential, seals the credential beside the model key and never journals it, and treats everything else as the Environment's own configuration. There is no server-side routes file. Brain does not care whether the code behind the protocol is inside brain-server, in the application's browser, or on another server. Brain ships two Environments of its own: the brain env, hosted inside brain-server, and the host env, whatever process registered as a host, a browser tab, a Node process, or a server, reached over the connection it holds open. The `driver` field on the wire says which of the three cases an entry is, `brain`, `host`, or `http`; applications never write it. How Brain reaches an Environment is an implementation detail Brain can extend without changing what a Tool or a session declares.
3. Brain's own Environment is processed like any other. It is one adapter registered under its name, answering setup, attach, invoke, call, detach, teardown, and turn through the same interface as every other Environment, and hosted in-process so latency stays small. No code path tests for its name. The adapter interface carries the session's services, so an in-process Environment can emit, publish telemetry, call the model, and dispatch Tools; an Environment that cannot carry an operation answers that it is unsupported. The SDK calls it `brainEnv`. The runtime it uses is its own detail and not part of its contract.
4. `driver` is a sibling of `configuration` in an Environment declaration, not a key inside it, and so are the `url` and credential of an HTTP Environment. Configuration is the Environment's own options, opaque to Brain, and nothing else.
5. Brain does not carry what a Tool needs at run time and does not match Tools to Environments. Binding values, binding names, and their redaction are removed from the session contract, the Environment protocol, and the SDK factories. A Tool's code obtains what it needs through the platform of its Environment, as ADR-022 already states. An Environment that grants access to something, a filesystem root, a network origin, or a secret, does so in its own configuration and by its own rules; Brain's own Environment keeps its allow-listed grants as its own options.
6. A Tool still declares what it needs, and the declaration is for its Environment, not for Brain. `needs` is a list of URIs on the Tool declaration, the same list for every kind of Environment. `pkg:` names software as a Package URL (ECMA-427). `https:` and `wss:` name a network destination, with the Content Security Policy leading-host wildcard, `https://*.example.com`, when a family of hosts is meant. `file:` names a filesystem location (RFC 8089), read-only unless it carries `?access=write`, the qualifier syntax purl already uses. Nothing runtime-specific belongs in the list: a Wasm Tool's WASI imports are a detail of its artifact that the Wasm Environment reads from the binary, running a program is `pkg:` in an Environment that runs processes, and a secret is either the URL a Tool loads it from or the Environment's own business. At setup Brain forwards the needs of everything placed in the Environment as one list; the implementation descriptor travels with each invoke; Brain checks nothing about either. Environments no longer declare resources to Brain; the resource-name grammar, the declaration format, and the create-time comparison are removed. Each Environment documents which schemes it honours and how, and refuses at setup what it cannot, naming the URI. Brain passes the list to the Environment however it reaches it and does not care what the Environment does with it. An Environment sees the needs of exactly the Tools placed in it before it is ready, so it provisions only what this session uses: Brain's own Environment computes its preopened directories and allowed hosts from the list, bounded by the deployment allow-lists, instead of taking them as per-session options.
7. Setup carries the Environment's configuration and the needs of everything placed in it, in one operation, and nothing about which Tools or which loop: an Environment provides resources and learns what runs only when asked to run it. Each invoke carries the Tool's implementation descriptor, its needs, the input, and the deadline; each turn carries the loop's id, configuration, needs, and input. The separate attach step goes. Detach at end and teardown at delete remain two operations, because end and delete are different moments under ADR-036.

## Alternatives considered

Keeping two Tool forms preserves a distinction Brain never acts on beyond routing, and every consumer of the configuration has to understand both. Wrapping the application host in a server-managed Environment resource, as ADR-028 did, is what ADR-033 rightly rejected; naming it as an entry inside the session's own configuration creates nothing server-side. Leaving the built-in Environment on its own path keeps seven string checks and a bypass that any new driver has to be taught about. Keeping binding values as a convenience makes Brain a secret carrier with a redaction obligation and no check behind the promise. Keeping the create-time needs check catches a misconfiguration one step earlier, at the first call rather than at create, and costs Brain a resource vocabulary it never interprets and forces every Environment to declare its whole surface up front. Runtime permission vocabularies, Deno's and Node's nouns or WASI interface names, are well understood but each belongs to one runtime; a list that one kind of Environment cannot read is not a universal declaration, whereas every runtime reads a URI. A structured form such as RFC 9396's authorization details would express actions on an API; one URI per need is enough today and grows into that shape without a redesign.

## Consequences

ADR-033's sentence that a resident Tool needs no synthetic Environment is restated rather than reversed: nothing is created beyond the session's own named entry, and its rule that a placed extension has exactly one explicit binding now applies to every Tool. ADR-034 is unchanged; the worker is the built-in Environment's internals. ADR-023 is unchanged; the services the adapter carries are the same services the turn already has.

The session and Tool contracts lose `hosting`, `host_id`, `binding_names`, `bindings`, and the binding-value schema; the redaction code goes. The Environment protocol loses the attach operation, the manifest and provision types, and the resources field on its receipts; the server loses its routes file, default endpoint, and default key, and gains a sealed per-environment credential beside the model key; the session configuration loses the resources recorded per Environment; the resource-name pattern, the resources type, and the bind check go. Validation collapses to one rule, every Tool names a bound Environment, with the Environment accepting or rejecting the needs it is handed at setup and the implementation it is handed at invoke. A Tool bound to an Environment that cannot serve it fails at setup if the Environment checks, or at the first call if it does not; Brain reports either honestly and does not pre-empt it. The host registration table becomes the host env's adapter and keeps registration, the command stream, results, and host-emitted Events. A loop may run in any Environment, including one reached over HTTP on another server; that needs Brain's turn services reachable from that process, so an HTTP Environment receives a per-turn callback address and token with the turn and the services become session routes. Until that lands, `turn` over HTTP answers unsupported, and ADR-033's statement that remote Agentloops are not shipped ends when it does. The Agentloop declares `needs` exactly as a Tool does; they join the others at setup, and its id and configuration arrive with the turn. Settings prefixed `BRAIN_WASM_` belong to the built-in Environment and are renamed with it; they remain the deployment's ceiling on what that Environment may grant, while the per-session network and filesystem options on the SDK factory go, since the grants now come from the needs. An Environment that installs software maps each purl type to its package manager, or delegates to an installer that already speaks that shape, and Brain's own Environment refuses `pkg:` needs because a Wasm sandbox installs nothing. Docs that describe two Tool forms describe one, with the host env as one Environment among others, and the resources and authority sections describe what an Environment does with the needs it receives rather than what Brain checks.
