## Request flow

1. **Client to Brain:** Your backend sends authenticated HTTP requests to Brain. Brain writes incoming messages to disk, queues them per session, and spawns or reuses the harness runner process.
2. **Brain to Harness:** The harness (**Pi**) runs in a child process over stdio. It constructs prompts, calls the LLM provider, manages context compaction, and decides when the turn is finished.
3. **Brain to Tools:** When the model calls a tool, the harness forwards the call to Brain. Brain attaches the authenticated `tenant_id`, `session_id`, and `call_id` and POSTs the call to the configured HTTP/SSE tool endpoint.
4. **Streaming to observers:** As the turn runs, Brain appends durable events to disk and broadcasts both durable events and live deltas (`assistant.delta`, `tool.progress`) to connected SSE clients.

## Local state vs. external checkpoints

Active sessions run against local disk so turns never block on remote storage:

- **SQLite** stores session metadata, tenant ownership, and frozen session config.
- **Append-only files** store the session event log and native harness state.

When external persistence is configured (local archive directory, S3, or R2), a background worker uploads 64 KiB transcript blocks and completed native checkpoints asynchronously. If a machine crashes before a background upload finishes, only the unsynced tail is lost; restoring from external storage always lands on the latest complete checkpoint.

## Ownership boundaries

| Layer | Responsibility |
| --- | --- |
| **Brain** | HTTP API, tenant auth, input queueing, SSE streaming, tool dispatch, local state, background checkpoint sync, OpenTelemetry. |
| **Harness** | LLM requests, prompt construction, context compaction, native session state. |
| **Tool service** | Tool execution, sandboxes, external jobs, human approvals, retries, resource cleanup. |
| **Host platform** | End-user auth, session routing/placement, single-owner enforcement, scaling, failover. |
