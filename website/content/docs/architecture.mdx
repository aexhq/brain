Brain sits between your application and the systems that do the work. It accepts authenticated requests, keeps each session's state on local disk, runs a harness process for each active session, and calls your tools over HTTP. This page follows one message through Brain and explains where state lives and which component owns what.

## How a message flows

<Steps>
<Step>
### Your backend sends a message

Your backend calls Brain over HTTP with a tenant's API token. Brain checks the token's grant, appends the `user.message` event to the session's log on disk, and queues the message. Each session runs one turn at a time; further messages wait in order.
</Step>

<Step>
### Brain runs the harness

Brain starts the session's harness runner, or reuses the one already running, and talks to it over stdio. The harness (Pi) builds prompts, calls the model provider, compacts context, and decides when the turn is finished. The runner process gets a minimal environment; Brain passes it the provider API key when it opens the session.
</Step>

<Step>
### Brain calls your tools

When the model calls a tool, the harness hands the call to Brain. Brain checks that the tool is enabled for the session, assigns a `call_id`, and records a `tool.call` event. It then validates the arguments against the tool's input schema and sends the call to the configured HTTP, SSE, or MCP endpoint with the authenticated `tenant_id` and `session_id`. Brain records the outcome as a `tool.result` event and returns it to the harness.
</Step>

<Step>
### Brain streams events

As the turn runs, Brain appends retained events to the log and broadcasts them, together with live-only `assistant.delta` and `tool.progress` events, to connected SSE clients.
</Step>

<Step>
### Brain records a checkpoint

When the turn completes, Brain records a checkpoint: the position in the event log and the harness's native state files. If external storage is configured, a background worker uploads it.
</Step>
</Steps>

## Local state and external checkpoints

Active sessions run against local disk, so a turn never waits on remote storage:

- **SQLite** stores session metadata, tenant ownership, and the session config fixed at creation.
- **Append-only files** store each session's event log and native harness state.

External persistence is optional. When you configure it, a background worker uploads immutable 64 KiB event-log blocks and completed native checkpoints to a local directory, Amazon S3, Cloudflare R2, or Google Cloud Storage. An optional PostgreSQL index lets `GET /sessions` list sessions stored by other instances.

When a request names a session that isn't on local disk, Brain loads the session's latest checkpoint from external storage. The loaded session is `interrupted` until you resume it. You can also force an upload with `POST /sessions/{id}/flush`, check upload progress with `GET /sessions/{id}/sync`, and restore a specific checkpoint with `POST /sessions/{id}/restore`.

<Callout type="warn" title="Unsynced data">
If a machine fails before a background upload finishes, only the unsynced tail is lost. Restoring from external storage always lands on the latest complete checkpoint.
</Callout>

After a restart, Brain loads each session from local disk the next time a request uses it. A session whose turn was running when Brain stopped comes back as `interrupted`; resume it to continue. See [Persistence & recovery](/docs/guides/persistence) for configuration and for handing a session to another server.

## Ownership boundaries

| Component | Owns |
| --- | --- |
| **Brain** | HTTP API, tenant auth, input queueing, SSE streaming, tool dispatch, local state, background checkpoint sync, OpenTelemetry. |
| **Harness** | LLM requests, prompt construction, context compaction, native session state. |
| **Tool service** | Tool execution, sandboxes, external jobs, human approvals, retries, resource cleanup. |
| **Host platform** | End-user auth, session routing and placement, single-owner enforcement, scaling, failover. |

## How errors are handled

Brain separates three kinds of errors, so a failure in one layer doesn't look like a failure in another:

- **Request errors:** A bad request gets a `4xx` response and leaves the session unchanged.
- **Tool failures:** Denials, error statuses, timeouts, and dropped connections become `tool.result` events with `is_error: true`, so the model can react. Brain never retries a tool call.
- **Execution failures:** Provider errors, a broken harness process, or a failed disk write stop the turn and emit `session.error`. The session stays `interrupted` or `failed` until you resume it.

## Design principles

- **Keep the core small:** Harnesses own inference and context; external services own tools and approvals.
- **Fail explicitly:** Tool errors become tool results, and Brain errors stop the affected turn. Missing or corrupted state returns an error instead of silently starting a fresh session.
- **Bound every queue:** Input queues, SSE subscriber buffers, and storage retries all have limits. Health checks and SSE keepalives never call the model.
