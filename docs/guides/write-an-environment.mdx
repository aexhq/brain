---
title: Write an Environment
description: Define a typed placement factory and implement the remote Environment protocol.
---

An Environment extension has two halves:

- a small application-side factory that produces immutable configuration and binding values;
- a driver that implements Brain's `environment/v1` operations and executes placed implementations.

Use `brainWasm(...)` instead when Wasmtime with Brain's built-in capability policy is sufficient.

## Application-side factory

```ts
import { environment } from "@aexhq/brain";
import { z } from "zod";

export const sandbox = environment({
  driver: "acme_sandbox",
  options: z.object({
    image: z.string(),
    token: z.string(),
  }),
  configure: ({ image }) => ({ image }),
  bindings: ({ token }) => ({ API_TOKEN: token }),
  managed: true,
  idleTtlMs: 300_000,
});

const env = sandbox({ image: "node:22", token: process.env.API_TOKEN });
```

`driver` is the adapter name. `configure` returns the non-secret configuration stored with the
Environment. `bindings` returns named plaintext values that exist only through attachment; Brain
does not copy their values into the session journal. The factory result is immutable and is passed
to placed Tool factories as `env`. The current server requires `brainWasm(...)` for Agentloop
placement.

## Driver protocol

The generated schemas under `contracts/environment/v1` are the source of truth. Brain sends an
`EnvironmentCommand` containing:

- contract version and resolved Environment binding;
- session ID and committed journal sequence;
- Environment and attachment identities;
- one request: setup, attach, call, invoke, cancel, detach, or teardown.

The driver returns the same contract and sequence with one receipt: accepted, progress, result,
outcome, failure, or unknown.

Setup declares resource policies. Attach receives the placed Tool manifests and binding values.
Each manifest contains its schemas, `needs`, binding names, and an opaque `implementation`. A
`brain_component` implementation names raw Component bytes already admitted to Brain; another
descriptor belongs entirely to the driver.

## Correctness rules

Brain durably commits the operation before calling the driver and sends it once. The driver must:

- treat `{session_id, sequence}` as the stable operation identity;
- return the same terminal receipt for an already-completed identical operation;
- reject a conflicting operation rather than execute it;
- bind every invocation to the supplied Environment and attachment;
- return `unknown` when it cannot prove whether an effect happened;
- make cancellation best effort without calling uncertain work successfully cancelled.

Brain never automatically retries a known failure or an unknown outcome.

## Resources and authority

An attach succeeds only when the Environment declares every resource name a Tool needs and has
every named binding. The driver enforces actual policy at its platform boundary: mounts and users
for `fs` and `process`, egress rules for `net`, origin policy for `dom`, and scoped injection for
`secrets`.

The Environment receives no ambient Brain or product-control-plane credential. Use narrowly scoped
provider identities and keep mutable Environment state separate from the session journal.

## Lifecycle

Session creation performs setup and attach before reporting ready. End detaches. Managed
Environments close after their idle TTL; session deletion closes any Environment that remains. A
lost physical instance must result in a failure or unknown receipt; it must not be presented as a
silent restore of its files or processes.
