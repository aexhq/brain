---
title: Embed the runtime
description: Run sessions inside a Rust service you already own.
---

Use the server when you want a process to talk to. Use the crate when another Rust service already
owns startup, configuration, and deployment, and you want sessions inside it.

The crate is one session at a time. Your service opens the sessions directory, builds the
runtime every session shares, and starts each session with both:

```rust
// One writer thread and one live feed for the whole process.
let writer = brain::Writer::spawn();
let feed = Arc::new(brain::Feed::new(telemetry.clone()));

let runtime = Arc::new(brain::SessionRuntime {
    max_model_calls_per_turn: brain::DEFAULT_MAX_MODEL_CALLS_PER_TURN,
    max_turn_ms: brain::DEFAULT_MAX_TURN_MS,
    tool_deadline_ms: brain::DEFAULT_TOOL_DEADLINE_MS,
    loop_executor,
    model_executor,
    tool_executor,
    live: feed.live_sender(),
    telemetry,
});

// A new session: its own directory under `sessions/`, its genesis record, then the
// environments you attach, then the configuration that was actually granted.
let store = brain::SessionStore::create(
    &sessions_dir.join(session_id.as_str()),
    session_id,
    &serde_json::to_value(&config)?,
    writer.clone(),
    feed.clone(),
)?;
let creating = brain::Session::begin(store.clone(), runtime.clone(), &config, &opening_transcript)?;
let session = creating.complete(config)?;

session
    .message(brain_protocol::MessageRequest {
        input: "Explain the current changes.".into(),
    })
    .await?;
```

After a restart, open what is on disk. Every store comes back with a turn the last process
left running already closed by a `turn_failed` record whose code is `interrupted`; nothing is
replayed into the loop. Which of them to start, and when, is yours: the server starts a session
on its first request and suspends it again after its idle TTL.

```rust
for store in brain::SessionStore::open_all(&sessions_dir, writer.clone(), feed.clone())? {
    let session = brain::Session::open(store, runtime.clone())?;
    // ...
}
```

## You supply the ports

`loop_executor`, `model_executor`, and `tool_executor` are the same seams the server fills in. Fill
them differently and you get a different deployment without forking the runtime: your own transport,
your own placement. The loop executor receives the session's `TurnServices` and runs the loop
against them; the server's executor forwards to the Loophost worker over a socket, and yours could
run a loop in-process.

## What the runtime keeps

Writes still land before effects, and recovery still works the same way. The runtime does not become
more permissive because it is embedded: `Session::begin` and `complete` are the only ways a session
is admitted, and both hold the configuration to the same contract the server's callers meet.

## What stays yours

Which sessions exist, which are running, what to do with them after a restart, and when to forget
them. Where environments live and how they are found. Credentials, and how HTTP retries are
answered. Everything about product policy. The runtime has opinions about correctness, not about
your architecture.

## Telemetry delivery

The telemetry channel is bounded and never holds up a turn. Its worker drains queued records into
ordered batches and retries a rejected batch for up to 30 seconds. A sink may therefore receive a
batch more than once and must make duplicates harmless. Exhausted deliveries are counted and
reported through `telemetry_delivery_dropped` records when the queue still has room.

Telemetry remains best effort. For resumable event forwarding, consume the session event endpoint,
save its sequence cursor after the destination acknowledges a batch, and reconnect from that cursor.
The session's logs, rather than the telemetry queue, are the durable record.
