# Distributed tools implementation plan

Status: Draft  
Releases: HTTP/inspection/approval-tool example at R0; MCP at R2; provider catalog at R3

Brain connects harness tool calls to external implementations. Its transport path validates input, supplies authenticated scope, bounds I/O, correlates results, and reports telemetry. First-party catalog entries are external tool services or packages for those services, not handlers loaded into the Brain process. There is no Environment interface or resource scheduler in the core. Persistence adapters remain internal storage integrations, separate from agent-facing storage tools.

| Work item | Implementation | Acceptance |
| --- | --- | --- |
| T1 Invocation contract | Define selected tool descriptions, input schemas, optional output schemas, endpoint bindings, and transport deadlines. Carry authenticated tenant/session/call identity outside model arguments. Implement HTTP JSON results and bounded SSE progress followed by a terminal result. | Invalid input never reaches the provider. Output is validated and bounded while reading. A model cannot forge scope or choose an endpoint. Returning a result completes the invocation; no separate finish call is required. |
| T2 Inspection and approval example | Provide an external inspection tool using session-scoped Brain API credentials. Demonstrate an external approval tool/service with both a waiting response and a prompt return containing a request handle. | Inspection stays within granted sessions. Approval policy and decisions are enforced by the external service; Brain routes ordinary calls/results without an approval store, gate, or endpoint. |
| T3 MCP | Integrate a maintained SDK at the adapter boundary; use the current protocol required by the pinned integration. Map tools/resources, errors, progress, and cancellation without a second lifecycle vocabulary. | HTTP and MCP preserve the same scope and result semantics. Brain event replay remains independent of transport sessions. Unsupported behavior fails explicitly. |
| T4 Storage and research catalog | Add S3/R2 resource tools, provider-backed web search, and bounded HTTP fetch/content extraction. Use a shared search-result shape with namespaced provider options. Start with Brave and Tavily adapters, selected through configuration. | Real provider checks pass. Resource access stays within configured bindings. Fetch enforces the configured network policy through redirects and resolved destinations, with size/time limits. |
| T5 Compute tools | Package external managed/remote code execution tools, starting with one provider and adding Fly/Modal integrations as needed. Provider services own create/attach, execution, files, cancellation, expiry, and cleanup. | Brain invokes them through T1/T3 with no new core interface. The service tests its advertised isolation, resource bounds, and cleanup behavior; provider handles remain ordinary tool data. |
| T6 Browser bridge | Package an external bridge service for an authenticated outbound browser connection. It exposes ordinary tools and binds commands/results to session and browser/tab grants. | Brain needs no browser-specific transport. The browser need not expose a public listener. Reconnect never replays mutations; disconnect reports waiting/unavailability through tool semantics. |
| T7 Catalog delivery | Package first-party descriptors/external implementations and generate documentation/examples from them. Bind only selected session tools. Keep provider dependencies and credentials in their tool-service packages. | Every advertised entry has a tested example. Sessions do not receive every catalog schema by default. Internal persistence credentials are never reused as agent-facing storage authority. |

The descriptor is configuration, not authority. Access derives from authenticated registration and host configuration. A tool's read-only hint cannot grant permission. Customer endpoints and code remain outside the core process; Brain enforces its configured outbound destination policy. Tool services enforce authorization for their resources and approvals for their actions. The action service must enforce any required approval; merely asking the model to call a separate approval tool is insufficient.

Use an invocation ID for correlation, without a public execution/job entity. An async HTTP handler or SSE stream can still leave the harness waiting for its terminal result. For independent work, a tool may return a handle immediately and offer status/cancel tools. Late notifications enter through a tested harness input path; receiving an event does not itself guarantee a model call. Brain neither invents tool success nor schedules polling for the model.

Brain does not automatically retry a tool invocation. An external service may implement retries under its own idempotency contract. A timeout or disconnected transport becomes a tool error, including an unknown-outcome indication when needed. Cancellation is a request to stop, not proof of rollback. A quiet tool stream is not evidence that the harness process died.

Keep tool data inside a result envelope, separate from protocol status. A business field named status does not control Brain. A tool failure is recorded as model-visible tool content and leaves the next decision to the harness/model. A Brain append failure or corrupted runner protocol stops the affected execution through a separate control/error path, even if the harness normally catches tool exceptions.

Large outputs remain in the tool service's storage; return a useful summary and scoped reference. Brain bounds data before buffering it and preserves supported media semantics. Resource identifiers are not credentials. Each external service owns artifact retention and resource cleanup, including what happens when Brain disappears.

The execution catalog covers short code execution, long-running commands, and caller-managed executors. Provider-specific functions stay in those tools; Brain does not normalize every compute provider into a common lifecycle. A filesystem snapshot is not a saved running process.

Disable native harness tools that would execute agent work locally or bypass configured remote bindings. Only adapter glue runs with the harness; customer implementations are external. Prove this for each supported harness before advertising the distributed-tool configuration. The [harness plan](03-harness-adapters.md) owns that check.

Catalog provider entry points include [Fly Machines](https://docs.fly.io/machines/api/machines-resource), [Modal Sandboxes](https://modal.com/docs/guide/sandboxes), [Brave Search](https://api-dashboard.search.brave.com/app/documentation/web-search/get-started), and [Tavily Search](https://docs.tavily.com/documentation/api-reference/endpoint/search). Verify exact capabilities against pinned dependencies during implementation and record them in tests and descriptors.

Use the official [MCP Go SDK](https://github.com/modelcontextprotocol/go-sdk) for protocol behavior. Avoid implementing an additional protocol stack, cloud abstraction framework, or dynamic package installer merely to populate the catalog.
