title: Environment

An environment is somewhere tool calls actually execute. Brain drives its lifecycle over the
`environment/v2` HTTP contract:

`setup` · `attach` · `call` · `invoke` · `cancel` · `detach` · `teardown`

The adapter implements them. Brain decides when they happen.

## Capabilities: the typed vocabulary

An environment *provides* capabilities — named, schema-fixed interfaces from a closed set:

| Capability | What it is |
| --- | --- |
| `exec` | run a shell string; buffered, bounded `{exit_code, stdout, stderr}` |
| `fs` | read/write/list under a workspace root; bytes as base64 |
| `net` | one outbound HTTP fetch under a policy |
| `js` | evaluate a source string in the environment's realm |
| `page` | the non-eval browser residue: navigate, screenshot, trusted input, pulled console |

The setup and attach receipts report `provides: [...]`, and Brain checks every bound tool's
`requires` against it at session create — a bash tool bound to a browser environment is a
create-time rejection naming the capability, the tool, and the environment, not a runtime
mystery. Growth of the set is a contract release, not an author convention.

An environment authored with the SDK registers providers with `provide.exec(...)`,
`provide.fs(...)`, and so on; the registered set is exactly what its receipts report. It
can also host provisioned tools with `host.esm()` — the SDK owns the host runtime, wiring
each hosted tool's handles to the environment's own providers in-process, so a capability
call from a hosted tool never crosses a wire. See
[Write an environment](/brain/docs/guides/write-an-environment).

## Attach carries the typed policy

`attach` carries three typed fields, replacing the untyped grant and adapter blobs of v1:

- **`grants`** — per-capability policy the environment enforces: `exec` time and output
  bounds, an `fs` root, a `net` host allowlist. Tools cannot see grants, only hit them.
- **`provisions`** — tool artifacts to host: each a `tool/v1` manifest plus the content
  identity of its payload, so re-provisioning is idempotent.
- **`bindings`** — named values injected into hosted tools at runtime. They travel on this
  wire only; the journal records their identities, never the values.

## Invocation is one envelope

A tool call arrives as `invoke {call_id, tool, input, deadline_ms}` and returns exactly one
outcome: `ok | error | timeout | cancelled`. The deadline is Brain's to enforce — an overdue
call is killed by the caller and recorded as a distinguished `timeout` outcome, because no
remote can be trusted to stop on its own.

## Addressed by object, not by connection

The exact Environment object a tool factory's `env` option names identifies one logical
attachment. Several Tools using the same object share it; calling the environment factory
again creates another attachment.
The generated private identity resolves to provider state rather than whichever process happens to
hold a socket.

Connections are caches. They never decide identity, and they never decide teardown.

## Replay is explicit

Every operation carries a stable identifier and the identity of its request. When a redelivery arrives,
the adapter can tell "this is the same call again" from "this is a new call that looks similar", and
Brain never replays an ambiguous effect against a replacement target.

## The official adapter

`@aexhq/env-aws-microvm` runs tools in an AWS MicroVM. It uses only the public
contract, so a third-party adapter is not a second-class one. See
[Write an environment](/brain/docs/guides/write-an-environment).

An application process answering tools is not an environment at all — Brain routes
those itself over the serve feed (see [App tools](/brain/docs/guides/app-tools)).
