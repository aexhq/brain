---
title: Environments
description: Explicit placement, authority, resources, and lifecycle for Components and Tools.
---

An Environment is an immutable placement and authority specification. Every Agentloop and every
placed Tool names one when its factory is called. Brain records the choice in session creation and
does not infer, rank, or substitute another Environment. The current server executes Agentloops
only in `brainWasm(...)`; driver-backed Environments currently host placed Tools.

## Brain Wasm

`brainWasm(...)` selects Brain's built-in native Environment for WebAssembly Components:

```ts
import { brainWasm } from "@aexhq/brain";

const isolated = brainWasm({
  network: { allow: ["api.example.com", "https://models.example.com"] },
  filesystem: { scratch: true, workspace: true },
  secrets: ["MODEL_TOKEN"],
});
```

Network entries are HTTP(S) origins or authorities, writable scratch and workspace access is
explicit, and secret names are identifiers. A caller request cannot grant itself authority: every
requested network target must also appear in `BRAIN_WASM_NETWORK_ALLOW`, every secret name in
`BRAIN_WASM_SECRET_ALLOW`, and each writable root in `BRAIN_WASM_FILESYSTEM_ALLOW`. The defaults
grant none. The server starts a fresh Wasmtime instance for each invocation under the resulting
policy. Each invocation receives a fixed 10 billion Wasmtime fuel units for guest computation;
model, Tool, HTTP, and filesystem waits consume no fuel. Fuel is a Wasmtime work allowance, not an
exact CPU-time promise. The separate `BRAIN_MAX_TURN_SECS` limit still bounds the whole turn's wall
time.

## Driver-backed Environments

An Environment extension maps typed application options into a driver configuration and optional
binding values:

```ts
import { environment } from "@aexhq/brain";
import { z } from "zod";

const remoteService = environment({
  driver: "remote_service",
  options: z.object({ url: z.url(), token: z.string() }),
  configure: ({ url }) => ({ url }),
  bindings: ({ token }) => ({ API_TOKEN: token }),
});

const env = remoteService({
  url: "https://tools.example",
  token: process.env.TOOL_TOKEN,
});
```

`configure` produces the immutable configuration Brain records and sends to the driver. `bindings`
produces plaintext values used only during attachment; the session journal records their names, not
their values. Resource TTL and allocation policy belong to the provider configuration.

The same Environment object can place several Tools in one session:

```ts
const session = await brain.sessions.create({
  model,
  agentloop: loop({ env: brainWasm() }),
  tools: [read({ env }), write({ env })],
});
```

## Resources and implementations

At attachment the Environment declares named resources such as `fs`, `process`, `net`, `dom`,
`secrets`, or a namespaced vendor resource. Brain verifies each placed Tool's `needs` by name before
the session becomes ready. The policy block is enforced by the Environment's real boundary, such as
filesystem mounts, process identity, egress rules, or IAM.

The Tool's `implementation` is opaque to Brain unless it is a Component admitted by content
identity. A driver interprets other implementation descriptors. There is no source-language or
package-building protocol in Brain.

## Lifecycle and delivery

An Environment declaration belongs to one session; reusing the same SDK object in another session
creates another logical Environment. Session creation performs setup and attachment before readiness;
these operations can declare capabilities without allocating a browser or sandbox.
Brain journals lifecycle and Tool intents before dispatch and sends each operation once. It records
a terminal receipt or an unknown outcome; it does not retry automatically. Ending a session
detaches it; session deletion asks the provider to tear down the logical Environment. A provider
wrapping an externally owned URL can implement teardown as releasing only its binding. Brain does
not acquire ownership of the external service.

Environment files and process state follow the Environment lifecycle. They are not durable session
state; the canonical session journal survives independently.

Providers can allocate on first invocation, serialize concurrent initialization, and expire physical
resources while sessions remain suspended. The standalone [lazy Environment example](https://github.com/aexhq/brain/blob/main/examples/lazy-environment.mjs)
demonstrates that policy using the existing wire. A restart creates fresh resources; it is not file
restoration. Reloaded metadata starts with unknown resource status until an operation observes it.
Environment and Tool failures are committed for the Agentloop before their results return.

Configure independent provider routes in `BRAIN_ENVIRONMENT_ROUTES_FILE`, or use the public registry's
`with_route` composition method. Route names are server-granted; the session's bindings stay fixed.
The complete `tool-env` Tool, mutable bindings, and automatic placement remain post-MVP.
