---
title: Agent loop API
description: Read context, call models and tools, and save decisions between activations.
---

A custom loop decides what the model sees, which tools run and when a turn finishes. Brain
supplies saved conversation and events, executes requested calls, and saves your loop's changes.
Start with [Write an agent loop](/brain/docs/guides/write-a-loop); use this page for exact behavior.

## What a run receives

Brain calls your exported `turn(input)` for a user message or an actionable background tool or
environment observation. Only one activation runs at a time per session. In the packaged
JavaScript example, parse these fields with `JSON.parse`:

| Field | Value after parsing |
| --- | --- |
| `input.inputJson` | `{ message, media? }`, or `null` for a background activation |
| `input.transcriptJson` | Saved model messages |
| `input.kvJson` | Saved loop state, keyed by name |
| `input.eventsJson` | New committed events, in sequence order |
| `input.configurationJson` | Options supplied through the loop factory |
| `input.toolsJson` | Tool definitions and their authorized environments |

`input.system` is the system prompt as plain text. `input.runtime` supplies logical time and a
deterministic seed. Return `{ resultJson: undefined }` or a JSON-encoded optional result.
Returning does not save local variables, update the transcript or acknowledge events.

## Call Brain services

These are the synchronous JavaScript bindings used by the authoring guide:

```js
import * as host from "brain:agentloop/host@0.2.0";
```

| Operation | Result and use |
| --- | --- |
| `host.model(requestJson)` | JSON model result; asks the session's model with your chosen messages |
| `host.dispatch(callsJson)` | JSON array of tool returns, in call order |
| `host.events(after)` | JSON event page; continue from `next_cursor` for more history |
| `host.emit(kind, payloadJson)` | Committed sequence of your application-visible event |
| `host.setTranscript(messagesJson)` | Committed sequence of the saved conversation change |
| `host.kvRead(key)` | JSON value string, or `undefined` if absent |
| `host.kvPut(key, valueJson)` | Committed sequence of one state write |
| `host.kvDelete(key)` | Committed sequence; deleting an absent key is a no-op |
| `host.acknowledge(through)` | Committed sequence of the processed-events marker |
| `host.environments(requestJson)` | JSON response to an authorized environment operation |
| `host.telemetry(recordJson)` | Best-effort diagnostics; not saved conversation history |

Sequence arguments and results use JavaScript `bigint`. Convert JSON event sequences with
`BigInt(event.sequence)` before passing them to these bindings.

### Model calls

```js
const messages = JSON.parse(input.transcriptJson);
const reply = JSON.parse(host.model(JSON.stringify({
  messages, system: input.system, tools: [],
})));
messages.push(reply.message);
host.setTranscript(JSON.stringify(messages));
```

This is an excerpt inside `turn`, after you have added any new user message. Model calls record
their request and result but do not change the saved transcript. Save only the replies you want
in the conversation; auxiliary summaries or classifications can remain separate.

Keep native model blocks unchanged when retaining context. Images and PDFs need their media
blocks, not merely URL text. Brain does not host or refresh those files. See
[models](/brain/docs/concepts/model) for format and provider compatibility.

### Tool calls

Each call names a tool and one authorized environment:

```js
const returns = JSON.parse(host.dispatch(JSON.stringify([{
  call_id: "lookup-1", name: "lookup_order", environment: "app", input: { id: "A-1001" },
}])));
```

Use names from `input.toolsJson`; the example assumes the app placed `lookup_order` in `app`.
Each return contains `call_id`, the original call `sequence`, ordered `events`, and `finished`.
Read `tool_result_emitted.data.result` for a result and `tool_call_ended.data.outcome` for completion.
There may be several results or none. A successful empty finish is a completion boundary, not a
null result. Inspect failures and uncertainty before presenting output as success.

A return releases the synchronous caller; the tool may keep running. Later results can activate
the loop without user input. Decide whether to call the model or wait for another message, and
avoid presenting the same observation twice. Model-facing tool definitions do not grant execution
authority. With several placements, your loop must choose one; dynamically created environments
also require their current `environment_sequence`.

### Environment control

`host.environments` accepts the operations described in
[environment control](/brain/docs/guides/environment-control), under the loop's grants. For example,
`JSON.parse(host.environments('{"operation":"list"}'))` returns visible environment views.
Tool and environment-handler contexts expose `ctx.environments`; this packaged loop binding uses
`host.environments`. There is no additional universal loop `ctx` SDK.

## Save state before acknowledging events

Save transcript and key/value changes before calling `host.acknowledge(through)`. Acknowledge
deliberately ignored events too. The processed marker, `brain.last_activation`, cannot move
backwards or beyond committed history; update it through `acknowledge`, not a normal KV write.

Each write is saved independently before returning. A later failure preserves earlier writes;
separate writes are not a transaction. Stored JSON `null` is distinct from an absent key.
Local memory does not survive the next activation.

## Failure and cancellation

Brain records requested effects before dispatch and records observations before returning them.
It sends each effect once and never automatically retries an uncertain action. Let the model or
caller explicitly decide another attempt after inspecting a failure.

Propagate service errors unless your loop has a deliberate handling policy. Cancellation or a
reached budget makes service calls fail with `cancelled` or `decision_limit`; cancellation does
not undo external actions. Background tools retain their original deadlines and budgets.

Test a second message, background activation, failed tool and cancellation as well as the first
answer. The [Rust reference loop](https://github.com/aexhq/brain/tree/main/examples/reference-agentloop)
shows a complete model-and-tool policy; the authoring guide supplies build commands.

## Other bindings

Rust and Python entry points and build requirements are in the
[language examples](/brain/docs/guides/write-a-loop#language-choices). An HTTP-hosted loop uses
the [Environment callback API](/brain/docs/reference/environment-protocol#invocation-services).
Names and asynchronous behavior differ between bindings.

For authors of new language or runtime adapters, the packaged binding specification is
`@aexhq/brain/contracts/agentloop.wit` (`brain:agentloop@0.2.0`), and JSON payload schemas are in
`@aexhq/brain/contracts/session.json`. Ordinary loop authors can use the operations above without
reading those specifications.
