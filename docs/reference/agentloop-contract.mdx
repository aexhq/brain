title: Agent loop contract
description: Host services, saved state and event handling for loop authors.
---

Brain does not compile Agentloop source. Write the loop in any language that can produce a
WebAssembly Component implementing Brain's WIT world, build it with that language's toolchain, and
give the resulting bytes to `component(...)`.

## Contract

The source of truth is
[`crates/brain-env/wit/agentloop/agentloop.wit`](https://github.com/aexhq/brain/blob/main/crates/brain-env/wit/agentloop/agentloop.wit).
The Component exports `turn` and imports these Brain services:

- `events(after)` reads a finite `EventPage`; continue from `next_cursor` for more history;
- `acknowledge(through)` durably advances the processed-through sequence;
- `model` performs a model call;
- `dispatch` invokes Tools and returns their synchronous observations as `ToolReturn[]`;
- `emit` appends an extension Event and returns its committed sequence;
- `set-transcript` durably replaces the saved conversation with the supplied messages;
- `kv-read(key)` returns an optional JSON string, distinguishing absence from stored null;
- `kv-put(key, value-json)` durably creates or replaces one value;
- `kv-delete(key)` durably removes a key; deleting an absent key is a no-op;
- `telemetry` publishes best-effort operational telemetry.

JSON strings on the WIT boundary use the generated session contract, also packaged as
`@aexhq/brain/contracts/session.json`. It includes `ModelRequest`, `ModelResult`, `ToolReturn`, `ToolResult`, and `EventPage`. An activation receives
optional user input, the current transcript, Agentloop kv, committed Events after its processed marker,
configuration, system prompt, Tool definitions with authorized Environment names, and a deterministic logical-time/seed envelope.
It returns only an optional result. Old transcript/kv fields in turn output are rejected.

Use `brain:agentloop@0.2.0`. Event-triggered activations omit user input (`input-json` is `null`
on WIT); do not synthesize a user message. There is one activation at a time per session.
Read `kv["brain.last_activation"]` as the processed marker and advance it through `acknowledge`,
not ordinary KV writes. Reading or returning does not acknowledge anything. Save selected
transcript/state changes first, then acknowledge every considered event, including dismissed ones.
The marker cannot move backwards or beyond committed history. Each acknowledgement returns
the sequence of its durable marker write.

Each `ToolReturn` contains `call_id`, the original call `sequence`, ordered `events`, and `finished`.
It can contain zero or multiple results. `tool_result_emitted.data.result` is a `ToolResult`;
`tool_call_ended.data.outcome` describes completion. A successful empty finish is a boundary,
not a null result. Present running status when needed and suppress already-presented events when
draining history. A later observation is ordinary context, not another provider reply to the same
Tool call. The official loops call the model for later results/completion and dismiss progress;
custom loops can instead retain history until another user message.

Await state services at the point the change should become durable. Each write returns its
committed sequence; later failure preserves completed writes. Separate writes are not a transaction.
Bindings expose `ctx.kv.read/put/delete`; the initial KV snapshot is a transport detail, not a
second mutable author API. KV deletion changes the projection, never earlier journal records.
Model calls record their actual request and result without changing the saved conversation, so an
auxiliary classification or summary request cannot replace it accidentally. Save the selected
conversation explicitly. Neither guest memory nor an unsubmitted local mutation survives activation.

Keep native model blocks unchanged when retaining their context. Common image/PDF blocks and
Tool-result media supply native model inputs through HTTPS URLs. The loop selects media from Tool
output and preserves required media blocks in auxiliary summarization requests. URL text alone does
not supply visual content. Brain does not host or refresh these files.
See [Model](/brain/docs/concepts/model) for adapter compatibility and format reset.

## Place the Component

```ts
import { agentloop, brainEnv, component } from "@aexhq/brain";
import { z } from "zod";

export const assistant = agentloop({
  options: z.object({ compactAt: z.number().min(0).max(1) }),
  implementation: component(new URL("./assistant.wasm", import.meta.url)),
});

const loop = assistant({ env: brainEnv({ name: "brain" }), compactAt: 0.8 });
```

`component(...)` also accepts `Uint8Array`, which is useful when bytes come from an object store or
another bundler:

```ts
import { readFile } from "node:fs/promises";

const bytes = new Uint8Array(await readFile("assistant.wasm"));
const assistant = agentloop({ implementation: component(bytes) });
```

For `brainEnv`, the client admits raw bytes through `POST /v1/agentloops` and constructs
`{ type: "brain_component", entrypoint: "turn", id }`. Admission is cached for that Component
object. An HTTP Environment instead takes its own opaque implementation descriptor, such as
`agentloop({ implementation: { type: "reference_agentloop" } })`. It requires no local admission
and receives invocation-scoped callback grants when executed. See
[Write an Environment](/brain/docs/guides/write-an-environment).

`ModelRequest.tools` contains full model-facing definitions. It does not grant execution authority.
Dispatch always names both the canonical Tool and an authorized Environment. When multiple
placements exist, implement an explicit selection policy or show the model a selector and unwrap
its arguments before dispatch. The reference loop requires a single placement per Tool.

## Effect semantics

The loop can request effects but does not perform Brain's model or Tool I/O itself. Brain durably
commits the intent, sends it once, and commits observations before returning them. A Tool's return
ends its synchronous phase; explicit finish ends its whole execution. Background results wake the
loop without changing the stored model transcript automatically.
Propagate host-service errors unless the loop has an explicit policy for presenting them to the
model or user. Let the model or caller explicitly choose another attempt after seeing the failure or unknown
outcome. Brain never makes that choice automatically.

## Test it

Test policy outside Brain with fake host imports, then run the compiled Component through the real
brain-env worker pool. Include cases for parallel Tool calls, unknown outcomes, cancellation, invalid JSON,
restart between turns, and a fresh Wasm instance on every activation.

## Standalone reference

[`examples/reference-agentloop`](https://github.com/aexhq/brain/tree/main/examples/reference-agentloop)
builds a usable model-driving Component using only Brain's public types and WIT. It reads failure
observations into the transcript, dispatches requested Tools, and returns errors to the model.
It has no Aex dependency. Build with `cargo build --manifest-path examples/reference-agentloop/Cargo.toml --target wasm32-wasip2 --release`.

Read imports are available during an activation. Collect observations before producing new effects
so the loop does not chase its own Events indefinitely, then save state and acknowledge the processed
prefix. Suspension leaves history readable; pending Tool observations can open a fresh activation.
Brain coalesces wakeups for five milliseconds from the first pending commit. Commits and live
acknowledgements remain immediate. Old activation services are fenced before final state capture.

Admission is explicit when desired: call `await brain.admit(placedLoop)` and
`await brain.admitTool(toolComponent)` before creation. Reuse those Component objects when placing
extensions; they cache successful admission. Brain retains compiled and prelinked templates,
never one session's credentials or heap.


## Packaged Python

`tools/build-python-fixtures.sh <output-directory>` uses pinned `componentize-py` to build the
Python Agentloop and Tool in `tests/fixtures/python`. They run in the same worker pool as Rust
Components and call Brain host services. Set `BRAIN_MAX_CORE_INSTANCES=1024` for these fixtures;
the default eight instances cannot hold their interpreter and generated adapters.

These small examples use `--stub-wasi`: they demonstrate Python computation and Brain callbacks,
and do not provide Python filesystem or network APIs. A package that needs WASI must link only
the worker's supported interfaces and be placed in an Environment with the corresponding grants. Brain does not install
Python or pip packages at runtime. Every execution has a fresh interpreter; persist Agentloop
state through `kv-put` and `kv-delete` and retain files only in an explicitly granted Environment workspace.
