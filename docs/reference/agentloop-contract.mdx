---
title: Harness protocol
description: Startup selection, lifecycle, native state, and journaled callbacks.
---

Brain selects one implementation from `--harness` or `BRAIN_HARNESS` before readiness.
Its JSON value has `command`, optional `args`, and optional `configuration`.
The command is deployment code. Session requests accept only `harness.configuration`
and `harness.environments`; executable fields and the old `agentloop` field are rejected.

## Transport and lifecycle

The process exchanges one JSON-RPC 2.0 object per UTF-8 line over stdin/stdout.
Both directions use request ids; diagnostics belong on stderr. The protocol is
`brain/harness/v1`. Rust types in `brain-protocol/src/harness.rs` define its payloads.

| Brain request | Parameters | Result |
| --- | --- | --- |
| `initialize` | `protocol, state_directory, configuration` | `protocol, name, state_version` |
| `session/open` | `session_id` | `null` |
| `session/run` | `session_id, sequence, model, input` | `{ result? }` |
| `session/cancel` | `session_id` | `null` |
| `session/close` | `session_id` | `null` |
| `session/delete` | `session_id` | `null` |
| `shutdown` | `{}` | `null` |

`sequence` names the activation's journal record. `model` supplies advisory model
metadata, not credentials. `input` contains optional user input, transcript, KV,
pending events, immutable tool declarations and current placements, system prompt,
session configuration, and the runtime envelope.

There is one active run per session. Different sessions can run concurrently.
Cancellation must be handled while run is pending. Initialization has a 30-second
deadline; cancellation has a five-second grace period before Brain kills the harness
process. Killing a shared process also fails its other active sessions.

## Callbacks

A harness requests `brain/call` with:

```json
{
  "session_id": "ses_12345678901234567890",
  "sequence": 3,
  "method": "model",
  "input": {
    "messages": [{"role":"user","content":[{"type":"text","text":"Hello"}]}],
    "tools": []
  }
}
```

| Method | Input / result |
| --- | --- |
| `model` | `ModelRequest` / `ModelResult` |
| `dispatch` | `ToolInvocation[]` / `ToolReturn[]` |
| `set_transcript` | `Message[]` / committed sequence |
| `kv_read` | key string / `{}` or `{ value }` |
| `kv_put` | `{ key, value }` / committed sequence |
| `kv_delete` | key string / committed sequence |
| `events` | sequence / finite `EventPage` |
| `emit` | `{ event_type, data }` / committed sequence |
| `environments` | `EnvironmentControlRequest` / operation result |
| `telemetry` | JSON record / `null` |

Callbacks work only during the named activation. Await every callback before returning.
An error contains `data.code` and `data.fatal`; fatal errors stop the activation even
when upstream catches them. The TypeScript binding aborts `ctx.signal` and calls
`cancel`. Brain drains already admitted callbacks before closing their authority.

Model and Tool requests cross durable journal barriers. Brain sends each effect once
and records an unknown outcome if a remote result is uncertain. Missing usage counters
remain absent. Upstream token estimates used for compaction are private runtime state.

## Native state and recovery

The harness identity and state version are bound to the data directory. A mismatched
identity refuses startup. Native state lives beneath `harness/<session_id>/`; closing
or passivating a session retains it, while session deletion removes it.

Brain records `brain.harness.activation` before entering native execution and removes
it only after successful completion. A remaining marker refuses subsequent execution,
including after restart. Create a new session after an interrupted or failed native
activation. The journal and transcript remain readable. This prevents an upstream
at-least-once recovery routine from replaying an uncertain tool effect.

The journal is authoritative for Brain's effects. Upstream files are authoritative for
agent continuation. There is no cross-harness checkpoint conversion or transactional
crash recovery spanning the two stores. Pre-0.40 active sessions are not compatible;
start with a new data directory.

## Upstream adapters

The image includes the pinned runtimes. For a standalone Node deployment, install the
SDK and only the runtime you use; these are optional peers so clients stay small:

```sh
npm install @aexhq/brain@0.40.0 @earendil-works/pi-coding-agent@1.2.0 @earendil-works/pi-ai@1.2.0
# Or Codex:
npm install @aexhq/brain@0.40.0 @openai/codex@0.162.1
# Or OpenCode, run with Bun 1.3.14:
npm pkg set 'overrides.@modelcontextprotocol/client=2.3.1' 'overrides.@parcel/watcher=2.6.0'
npm install @aexhq/brain@0.40.0 @opencode/sdk@2.0.28 @ai-sdk/provider@3.0.8
```

The OpenCode overrides replace upstream dependencies affected by high-severity
advisories. The image and conformance suite use these exact versions.

| Adapter | Configuration |
| --- | --- |
| Pi | `contextWindow?`, `maxTokens?`, `compaction?: { enabled?, reserveTokens?, keepRecentTokens? }` |
| Codex | `contextWindow?`, `compactAtTokens?` |
| OpenCode | `contextWindow?`, `maxTokens?`, `compaction?: { auto?, buffer?, keep?: { tokens? } }` |

Session values override deployment values. Missing context-window or output-limit
metadata must be supplied explicitly where required. Unknown keys fail.

Pi uses the complete coding-agent session SDK. OpenCode uses its embedded SDK with a
custom provider and tool catalogue. Codex uses its Rust app-server, dynamic tools, and
a local Responses gateway into Brain's model adapter; its dynamic-tool API is
experimental and version-pinned. All three delegate compaction to upstream, retain
opaque model continuation, exclude unadmitted tools, and disable transport retries.

Pi accepts HTTPS media and imported transcripts. Codex and OpenCode currently accept
text only and start from native state. All three keep a fixed tool-placement catalogue
per native session. A changed catalogue fails explicitly; incarnation references are
resolved from the current activation. Custom harnesses may support additional features.

## Environment control

Grant a harness access with `harness.environments`, and declare the corresponding
Environments in the session. Call `ctx.environments` in a custom implementation.
Upstream adapters do not invent management tools or interpret these grants as model
tools. See [Environment control](/brain/docs/guides/environment-control).
