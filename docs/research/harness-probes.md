# Harness feasibility evidence

Probed 2026-10-15 using the published packages, with an isolated working directory and recording model endpoint. These findings constrain the next adapter slice; they are not support claims.

## Codex 0.163.0

App Server over stdio accepted `thread/start` with `dynamicTools`, `environments: []`, and experimental API capability. A real outbound Responses request advertised `request_user_input` plus the single supplied `echo` tool. Disabling `shell_tool`, `image_generation`, `apps`, `plugins`, `memories`, `multi_agent`, `goals`, and `collaboration_modes` removed execution/delegation tools but did **not** remove `request_user_input`. No unrecognized settings were reported for that combination.

`environments: []` is useful: it disables environment access without creating an environment concept in Brain. Thread storage is an append-only rollout JSONL under the isolated Codex home. The full restore/compaction contract still needs a runner test.

That initial configuration did not establish an exact externally supplied tool set. The [later exclusion probe](#codex-catalog-exclusion-follow-up-2026-10-16) found and verified a separate registration control, without a native patch or outbound model proxy. An adapter must enforce this setting rather than silently accepting native approvals/questions.

Sources: [App Server](https://developers.openai.com/codex/app-server), [configuration reference](https://developers.openai.com/codex/config-reference), and the experimental JSON schemas generated by the actual 0.163.0 binary. The installed global 0.162.1 binary was not used for the outbound request probe.

## OpenCode SDK 2.0.30

The embedded SDK started and shut down on Node 24.17 with an isolated configuration directory, project/Claude config disabled, model catalog fetching disabled, and a local SQLite database. A transitive UI package declares Node >=26.4, so Node 24 compatibility requires further qualification even though this startup probe passed.

The shipped `@opencode/sdk` host unconditionally calls `SessionRestart.resumeSuspendedSessions` after registering plugins. The shipped core implementation appends a restart continuation message and starts claimed sessions. `ServerOptions` has no public passive-start toggle. `resume: false` on later inputs does not control this startup call.

An embedding replacement for `SessionRestart` or a pinned one-line host patch is feasible. It must be accompanied by an unclean-shutdown test that observes zero provider/tool calls during cold restore. The larger remaining problem is coherent incremental SQLite persistence: copying a growing database each turn would repeat the predecessor's quadratic-write mistake. Add a native export/snapshot adapter only after demonstrating bounded incremental writes and compaction recovery.

Sources: [SDK](https://opencode.ai/v2/docs/build/sdk/), [session design](https://github.com/anomalyco/opencode/blob/dev/specs/v2/session.md), and published 2.0.30 code at `sdk/dist/internal/host` and `core/dist/session/execution/restart` (bundled filenames can change).

## Local architecture spikes, 2026-10-16

[Startup, residency, transport, and concurrency measurements](application-sdk-spikes.md) exercised Pi 1.2.0, Codex 0.163.0, and OpenCode 2.0.30 against deterministic local model/tool fixtures. They compare dedicated and shared hosts, not completed Brain adapters or live-provider capacity.

The performance fixture still advertised Codex's `request_user_input` after disabling web search and the recorded execution/delegation features. It did not invoke that tool. The separate catalog follow-up below changed the configuration, not the recorded performance results.

The OpenCode fixture removed registered tools through `ctx.tool.transform()` and added only `echo` with `options.codemode: false`. Its model request nevertheless advertised a generated `execute` tool. The [published 2.0.30 implementation](https://unpkg.com/@opencode/core@2.0.30/dist/chunks/instance-j09zfasm.js) passes `{ code }` to a Code Mode runtime and installs an HTTP `fetch` extension. It describes a confined runtime without imports, direct filesystem access, or timers, not an unrestricted shell. It is still a local generated-code path, not an established inert descriptor. The tested per-tool setting neither removed the descriptor nor established that its executor was disabled. No code-mode invocation was performed; exclusion remains a qualification gate alongside passive startup and native SQLite recovery.

## Codex catalog exclusion follow-up, 2026-10-16

The pinned source separates tool registration from call-time availability. [Tool registration](https://github.com/openai/codex/blob/rust-v0.163.0/codex-rs/core/src/tools/spec_plan.rs) depends on the configuration value resolved from `tools.experimental_request_user_input.enabled`; the [question handler](https://github.com/openai/codex/blob/rust-v0.163.0/codex-rs/core/src/tools/handlers/request_user_input.rs) also rejects calls outside its allowed modes or from non-root agents. Advertisement alone therefore establishes neither successful invocation nor harmlessness.

Ran a separate two-case probe against the same installed Codex 0.163.0 binary and loopback provider fixture. The default configuration advertised `echo` and `request_user_input`. Setting `tools.experimental_request_user_input.enabled = false` in the `thread/start` configuration override advertised exactly `echo`. Each case completed two provider requests and one external `echo` call; startup made no provider requests. Neither case invoked the question tool, used a live model, or modified native code.

This verifies a control for the specific catalog gap, not a complete Codex adapter. Enforce it on all adapter-created/restored sessions and retain the passive-recovery, compaction, persistence, and shared-session isolation gates. The experiment source and result are retained as `codex-tool-exclusion.py` and `codex-tool-exclusion-results.json` with the other local spike artifacts.

## Current supported subset

Pi remains the supported runner. Third-party runners can implement the existing process contract, but Codex/OpenCode are not advertised as equivalent built-ins until the same passive-recovery, exact-tool, compaction, and append-efficiency fixtures pass. This keeps the session API unchanged and allows the remaining adapters to land independently of storage, MCP, tools, or deployment.
